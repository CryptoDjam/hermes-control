# Changelog

## 0.6.0 — 2026-10-06
Hardening release after the LocalAgents / Codex reviews. Tested target: Hermes 0.19 and 0.21.5, Paperclip 2026.1001.0.
- **R02a — empty `.env` on prepare**: after `hermes profile create --clone`, the new profile's `.env` is replaced by a mode 600 file holding only a comment header. No API key or Telegram token inherited from the instance (the instance's own `.env` is untouched).
- **Preparation lock**: `withPrepareLock(instanceHome, slug, fn)` — a lock folder `<instance>/.hermes-control/prepare-<slug>.lock` (atomic `mkdir`; stale after 10 min and taken over; otherwise a clear « préparation déjà en cours » error). Two triggers at once prepare an agent once.
- **Strict `companyInstance`** (`src/company-instance.ts`): the company's instance is the one named `slug(companyName)` in the workspace. No fallback on the first or the only instance; when none matches, preparation fails with a message listing the instances present and the expected name.
- **The instances view creates no profile, folder or link and runs no launcher**: opening the Hermes page never prepares an agent (`syncAll(..., { autoPrepare: false })`); only `agent.created` / `agent.updated` and the « Préparer l'agent » button do. The view still syncs the declared fields of linked agents (`hermes config set`) and writes `agents.json`. The view **never runs an agent's launcher**: `homeFromLauncherFile()` reads the `hermesCommand` script statically (text, ≤ 64 KB, `HERMES_HOME=…` with `$HOME`/`~`, `$PROJETC` = `<launcher dir>/../..` and any variable assigned literally above). `resolveHomeFromLauncher` stays exported but is `@deprecated` and no longer called.
- **Corrupted files are refused, never rewritten**: `readConfigStrict()` distinguishes an absent `config.yaml` (empty config) from an invalid one (YAML error, or not an object); `HermesProfile.configError` carries the message and such a profile is never synchronized (no `hermes config set`; sync record error « config.yaml invalide : … ; aucune écriture »). `agents.json` that is not a valid JSON object: `rememberAgent` refuses with an explicit error and leaves the file alone, `recallAgent` returns null. `agents.json` read-modify-write now runs under a lock (`agents.json.lock`, 2 s wait, stale after 30 s).
- **Single Telegram gateway guard**: `gatewayOwners()` reads `~/.config/systemd/user/hermes-gateway*.service` and their `HERMES_HOME`; `set-telegram` refuses when a gateway unit exists for another profile (the message names it) or when another known profile already has `TELEGRAM_BOT_TOKEN` in its `.env` (variable names only, never values).
- **R02b — assignment checked before wake (adapter)**: at run time the adapter reads `agents.json` first (`recallAgent(agent.id)`); an agent with no entry **refuses to run** (« agent non affecté à une instance Hermes : synchronise ou prépare l'agent dans Paperclip (page Hermes) »); so does an entry whose `home` has no `config.yaml` any more. No more name matching across all instances at run time; the adapter no longer writes the map. `detectModel` no longer guesses from the first profile found (it defers to the base adapter). `HERMES_CONTROL_HERMES_BIN` (explicit Hermes binary path) is honored before `~/.local/bin/hermes` in the adapter and as the plugin worker's binary.
- **Health in three states** (`src/health.ts`): `checkProfile(home)` measures the real socket path length (`join(home, "gateway.sock")` and every `*.sock` present; ≤ 100 bytes), parses the YAML front matter of every `skills/*/SKILL.md` (`hiddenByPlatforms` = invalid header with a `platforms:` line) and reports `configError`; `agentState()` → `installed` (profile present) / `connected` (`auth status` logged in) / `authorized` (connected + last sync without error; « authorized and tested » with a negative-case connection test is still planned). The `instances` data returns `health` (per profile) and `states` (per agent); `onHealth()` reports `degraded` with a short message when a socket path is too long, a skill is hidden or a config is unreadable. UI: an « État » column and one red line per health alert.
- **Review fixes** (second commit, same version): the adapter refuses when the launcher's `HERMES_HOME` (read statically) differs from the assignment or when the assigned `config.yaml` is invalid; R02a is idempotent (markers `<profile>/.hermes-control/{prepared-by-hermes-control,env-cleaned}`, `.env` emptied in a `finally` right after the clone, never through a symlink); `parseAuthStatus` tests negations first; stale locks are claimed by `rename` then `rm` (shared `src/lock.ts`); the launcher cache is keyed by path + mtime and never caches a miss; `homeFromLauncherFile` treats single quotes as literal, ignores `VAR=x command` lines, requires an absolute launcher and returns the real path; a launcher-derived home is only kept with a `config.yaml`; `profiles` must be the second-to-last segment; `gatewayOwners` handles several `Environment` pairs per line and compares real paths; `set-telegram` runs under a lock; YAML parsed with `uniqueKeys: false` (like `safe_load`); `HERMES_CONTROL_AGENTS_MAP` and an explicit user home (`HOME` else passwd) for `agents.json`, `workspace` and `roots`; `onHealth` reports `error` when the probe fails.
- **Corrections before service (third commit, same version — after Codex's review of f5d4327 and Cyril's decisions of 6 Oct)**:
  - **Assignments table — no assignment by name** (`src/assignments.ts`): the single source of truth is `~/.config/hermes-control/assignments.json` (`HERMES_CONTROL_ASSIGNMENTS` overrides): `{ schemaVersion: 1, companies: { [companyId]: { name, instances } }, agents: { [agentId]: { companyId, instanceHome, profile, name, assignedAt, assignedBy } }, approvedBinaries? }`. Validated on read **and** write: an agent's instance must be one of its company's authorized instances; two agents never claim the same profile; every instance is resolved by `realpath` inside a known root (`~/.hermes`, `roots`, `HERMES_CONTROL_ROOTS`, `<ws>/hermes/profils`); a corrupted file is refused, never rewritten. Atomic writes (tmp + rename, mode 600) under the lease lock. `agents.json` is now a **derived projection** (`schemaVersion`, `derivedFrom: { file, sha256 }`), rewritten only by the plugin from the table; the adapter reads the table directly and uses the projection only as a fallback with the same fingerprint; the flat 0.4–0.6.0 map (produced by name) is ignored and reported. `syncAll` **never calls `matchAgent` to assign**: an agent's assignment is its table entry; without one the record says « non affecté », nothing is written to Hermes, and a **suggestion** by name (restricted to the company's authorized instances) is shown, never applied. Renaming an agent changes nothing. Opening the view never writes the table. Actions: `set-company-instances` (company → authorized instances among the discovered ones), `assign-agent` (agentId, companyId, instanceHome, profile; board user; instance authorized, profile existing or the agent's slug to prepare), `unassign-agent`, and `prepare-agent` now takes an **explicit `instanceHome`** (authorized) and assigns at the same time. Automatic preparation on `agent.created` / `agent.updated` is **removed** (no default instance): events only sync already-assigned agents. UI: « Instances autorisées de l'entreprise » block, an « Affectation » column with the suggestion and « Affecter » / « Préparer et affecter » / « Désaffecter » buttons. `companyInstance` (instance named after the company) is removed. The adapter refuses an agent without a valid assignment for **its** company (`ctx.agent.companyId`), an instance no longer authorized, a profile claimed twice, or an absent / invalid `config.yaml`, even when « connected ».
  - **Launcher uncertainty refused** (`homeFromLauncherFile` → `{ home } | { error }`): an unresolved variable, a sub-shell, a conditional expansion, **several `HERMES_HOME` assignments** (« plusieurs HERMES_HOME » — the shell would apply the last), no `HERMES_HOME`, an unreadable, relative, binary or oversized launcher are explicit errors. The adapter distinguishes an **approved Hermes binary** (`hermesCommand` equal to `HERMES_CONTROL_HERMES_BIN`, listed in the table's `approvedBinaries`, or a bare name without « / ») from a **script**: for a script any uncertainty is a refusal, a divergence is a refusal, identical is OK. The real `~/Projects/ProjetC/hermes/bin/hermes-cmo` form is accepted (test).
  - **Durable prepare state, `.env` cleaned before use** (`src/prepare.ts`): `<instance>/.hermes-control/preparing-<slug>.json` (`{ startedAt, pid, stage }`) is written **before** `hermes profile create --clone`; the clone runs in `try/catch/finally`; after it the `.env` is emptied (rm + `wx` 600), then `env-cleaned`, then `prepared-by-hermes-control`, and only then `preparing-*` is removed. After a failed clone the `.env` is emptied and the state stays (`clone-failed`): the profile is **unusable** (`profileUsability`) — the adapter refuses it, as it refuses a profile created by Hermes Control without `env-cleaned` — until a new `prepareAgent` finishes the cleanup. A profile without those markers (made by hand) is never emptied. `config.yaml` present never means ready.
  - **Lease lock** (`src/lock.ts`): the lock folder holds `owner.json` (`pid, host, token, startedAt, renewedAt`); the holder renews its lease every 5 s; a lock is reclaimed only when the lease is stale (> `staleMs`) **and** the owner is dead (pid absent) or on another host; a living but suspended owner is never dispossessed; release only if the `token` is ours (an old holder never removes its successor's lock). Separate tests: abandoned lock, suspended living owner, successor's lock kept.
  - **Watchdog socket path** (`src/health.ts`): the exact paths of the pinned version are measured **before any start**, even with no socket yet: `<home>/gateway.sock`, `<home>/state/gateway.loop-tick.<pid>.sock` with a 7-digit pid (Linux `pid_max` 4194304), plus every `*.sock` in `home` and `home/state`; threshold 100 bytes; the adapter refuses to start a profile over it. An 80-byte root is red.
  - **Label**: state 3 is « **connecté et synchronisé** » (`synced`), never « autorisé »; « autorisé et testé » remains planned.
  - **Migration script** `scripts/migrate-assignments.mjs` (read-only by default, `--apply` to write): builds the table companyId, agentId, name, instance, real profile, launcher, statically read `HERMES_HOME`, binary, model-account label (never a secret value) from the existing `agents.json` + launchers + discovered instances (+ Paperclip `run-logs` folder names for the company id), reports every disagreement and warning (socket paths over 100 bytes), proposes `assignments.json`; `--apply` is refused while a disagreement remains and backs up the existing files first. Imports `dist/lib.js` (new build target) so it shares the plugin's code.
  - **Socket paths are measured on the launcher's literal HERMES_HOME (symlinked short roots work)**: `homeFromLauncherFile` returns `{ home, literal }` — `home` is the real path (assignment comparisons, unchanged), `literal` the `HERMES_HOME` as written after `$HOME`/`~`/variable expansion, without `realpath` (Hermes binds its sockets on the path it is given). The adapter measures `literal` for a launcher script (the assigned home for an approved binary); the view's health measures an assigned agent's profile on its launcher's `literal` (`socketBase` in the result). A launcher `export HERMES_HOME="$HOME/.h/d/profiles/assistant"` with `~/.h/d` → a deep root is accepted; the same profile written as the long path is refused.
  - 121 tests (plugin + adapter), up from 81; the six Codex probes are replayed with inverted expectations in `src/review-codex.test.ts`.
- Not in this release (still planned): `doctor` check of the plugin's `localPath` registration in Paperclip, the `--yolo`/skills contract test, the per-agent account listing (`doctor`), the « autorisé et testé » state, launchers generated from a manifest (the static reader still assumes `PROJETC` = `<launcher>/../..` for the ProjetC form), and the import of `assignments.json` into the pack's `identites.json`.

## 0.5.0 — 2026-10-04
- **An agent created in Paperclip gets its Hermes profile automatically.** With a shared workspace declared in `~/.config/hermes-control/workspace` (written by `hermes-paperclip-pack init`), a Hermes agent with no matching profile is prepared on `agent.created` / `agent.updated` and when the Hermes page is opened: `hermes profile create <slug> --no-alias --clone --description "<Name> — <title>"` in the company instance, `<ws>/agents/<slug>/{fiche.md, rapports/, memoire/{MEMORY.md,USER.md}, medias/{brouillons,valides,publies}/}`, `memories` → `agents/<slug>/memoire` (existing Hermes memory files are moved, never lost), `journal` → the profile's `logs/`, common skills of `<ws>/hermes/skills` linked, `SOUL.md` from `<ws>/modeles/`. Idempotent, never deletes. The 5-minute job (no company scope) never creates anything.
- **Page**: a « Dossiers communs » card (workspace paths), a **« Préparer l'agent »** button for agents without profile (action `prepare-agent`, board users only), and a **Telegram** column per profile: the bot token is written to `<profile>/.env` (mode 600) and `hermes gateway install --start-now` is run for that profile; the token is never read back, shown or stored in plugin state (action `set-telegram`, only for known profile paths). New capability `ui.action.register` (Paperclip refuses an in-place upgrade on new capabilities: uninstall / reinstall the plugin).
- **Adapter**: when the agent has no working directory in Paperclip, `cwd` defaults to `<ws>/agents/<slug>` if it exists.
- Known limit: Hermes installs one gateway service per user (`hermes-gateway.service`); several Telegram agents on one machine need `hermes gateway run` per profile (phase 2).
- 44 tests.

## 0.4.0 — 2026-10-04
- **Skills follow the agent into its Hermes profile.** The built-in Hermes adapter links Paperclip-managed skills into `~/.hermes/skills` (it resolves `$HOME`, never `HERMES_HOME`), but Hermes only loads `$HERMES_HOME/skills`. Since Hermes Control runs each agent on its own profile, the skills were invisible there (seen on CDjam: Chef could not find `first-task`). The adapter now links every skill assigned in Paperclip into `<profile>/skills/<name>` — on skill sync (the Skills tab) and at the start of every run — and removes the link when a skill is unassigned. Only links that point to a Paperclip source are ever removed; skills you placed in the profile yourself are left alone and listed read-only in the Skills tab.
- New shared map `~/.config/hermes-control/agents.json` (agent id → instance/profile/home), written by the adapter at run time and by the plugin at every sync, because Paperclip's `listSkills` / `syncSkills` hooks only carry the agent id.
- `listSkills` / `syncSkills` overrides: the Skills tab shows the real link path in the profile, and a warning when the agent's profile is not known yet.
- Nothing removed: Provider/Model menus, name → profile, provider/model/thinking sync and the instances view are unchanged. 33 tests.
