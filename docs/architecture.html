Hermes Control — Hermes moteur, Paperclip aux commandes

Plugin Paperclip signé Cyril M · version 0.6.0 (commits locaux f0f2957, 8dd4d6c ; non publiée), état au 6 octobre 2026, 17 h · code : ~/Projects/hermes-control/

1. Le principe

Paperclip est le maître. Pour chaque agent, Paperclip envoie cinq données : son nom, son working directory, son provider, son modèle, son thinking. Avec le nom, Hermes Control trouve le profil Hermes correspondant ; provider / modèle / thinking y sont écrits et Hermes tourne dessus. Dans l'autre sens, les menus Provider et Model du formulaire de base de l'agent listent ce que Hermes connaît. Depuis la 0.4, les skills cochés pour l'agent dans Paperclip suivent aussi : ils sont liés dans le dossier skills du profil Hermes de l'agent. Rien d'autre n'entre ni ne sort. Deux pièces dans un même projet : un adaptateur (remplace l'adaptateur Hermes intégré) et un plugin (synchro + une vue « instances »).

Règle d'or : une seule source de vérité, Paperclip. Hermes Control ne crée pas de page de réglages : il remplit les menus existants et recopie les choix dans Hermes. Les clés ne sont jamais lues ni affichées ; aucune commande ne passe par un shell.
Pourquoi un adaptateur : les menus Provider / Model du formulaire de base appartiennent à l'adaptateur Hermes de Paperclip, pas aux plugins. Paperclip permet officiellement de remplacer un adaptateur intégré par un adaptateur externe (pause / retour arrière à tout moment : paperclipai adapter override hermes_local).

Les skills suivent l'agent (0.4)

L'adaptateur Hermes officiel pose les liens des skills gérés par Paperclip dans ~/.hermes/skills (il regarde $HOME, jamais HERMES_HOME), alors que Hermes ne lit que $HERMES_HOME/skills. Avec un profil par agent, un skill coché dans Paperclip restait donc invisible (vu le 4 octobre : le Chef ne trouvait pas first-task). Hermes Control lie maintenant chaque skill désiré dans <profil>/skills/<nom> — à la synchro (onglet Skills) et au début de chaque passage — et retire le lien quand le skill est décoché. Seuls les liens qui pointent vers une source Paperclip sont retirés : les skills maison du profil (comfyui, rapport…) ne sont jamais touchés et apparaissent en lecture seule dans l'onglet. Comme ces appels de Paperclip ne portent que l'identifiant de l'agent, la carte agent → profil est tenue dans ~/.config/hermes-control/agents.json (écrite au passage et par la synchro du plugin).

Un agent créé dans Paperclip = un profil Hermes prêt (0.5)

Quand un dossier de travail commun est déclaré (~/.config/hermes-control/workspace, posé par hermes-paperclip-pack init), un agent Hermes créé dans Paperclip sans profil de ce nom est préparé tout seul : profil cloné de l'instance de l'entreprise (hermes profile create --clone), dossiers agents/<agent>/ (fiche, rapports, mémoire, médias), mémoire et journal liés, skills communs liés, SOUL écrit depuis les gabarits. Jamais de suppression ; relancer ne casse rien. La page Hermes montre les dossiers communs, un bouton « Préparer l'agent » en secours et, par profil, un champ jeton Telegram (écrit dans le .env du profil en 600, passerelle Hermes démarrée, jamais réaffiché). Sans dossier de travail déclaré, rien n'est créé automatiquement : sur ce PC (CDjam), ~/.config/hermes-control/workspace n'existe pas et la préparation automatique est inactive, volontairement jusqu'à la 0.6. Point à corriger en 0.6 : en 0.5, l'ouverture de la vue « instances » déclenche la même préparation que agent.created (effet de bord) ; la 0.6 rend la vue purement consultative.

La synchronisation Paperclip → Hermes

Déclenchée à chaque modification d'un agent (agent.updated / agent.created), à l'ouverture de la vue, et toutes les 5 minutes. Le plugin compare config.yaml du profil aux valeurs Paperclip et n'écrit que les différences : model.provider, model.default, reasoning_effort (thinking, seulement s'il n'est pas « auto »). Valeurs validées (lettres, chiffres, .-_:/), exécution hermes config set sans shell.

3. Comment le nom choisit le Hermes

  1. Le nom de l'agent est mis en minuscules sans accents : « Apolline M » → apolline-m, « Chef » → chef.
  2. On cherche un profil Hermes du même nom (profiles/apolline-m, profiles/assistant).
  3. Sinon, un profil dont la description commence par ce mot : « Chef — PDG… » → profil default de l'instance direction ; « CMO — … » ; « Chercheur — … ».
  4. Trouvé → le passage tourne avec HERMES_HOME de ce profil (plus besoin de lanceurs par agent) ; pas trouvé → le passage s'arrête avec la liste des profils connus.
  5. Les instances sont cherchées dans ~/.hermes et dans les dossiers listés dans ~/.config/hermes-control/roots (pour CDjam : ~/Projects/ProjetC/hermes/profils). Hermes Control a été testé avec Hermes 0.19 et 0.21.5 (CDjam : les 5 agents tournent en 0.21.5 depuis le 06/10, moteur ~/.local/share/hermes-0.21/, repli 0.19).
Thinking : Paperclip range le « Thinking effort » d'un agent Hermes dans ses arguments (--reasoning-effort) ; le plugin le recopie dans le profil Hermes quand il n'est pas « auto ».

4. Sécurité

  • Commandes hermes lancées sans shell (arguments séparés), noms de profils validés ([a-z0-9._-]).
  • state.db ouverte en lecture seule avec node:sqlite (rien à compiler).
  • Aucune clé lue, aucun réseau sortant (capacité http.outbound non demandée).
  • Correction du 06/10 : le worker écrit bel et bien : config.yaml du profil (synchro provider / modèle / thinking par hermes config set --force), création de profils, dossiers et liens (préparation automatique), .env du profil (jeton Telegram, mode 600). Ces écritures sont bornées aux profils connus et aux dossiers agents/<slug>/.
À savoir (relectures du 06/10). Hermes Control enveloppe l'adaptateur Hermes officiel et hérite de son comportement : chaque passage Paperclip lance hermes chat --yolo, donc aucune validation interactive, quel que soit approvals.mode. Avec terminal.backend: local, l'agent a les droits de l'utilisateur Unix, sauf ce que la liste deny bloque (et une liste par motif se contourne) : la protection réelle est deny + le backend d'exécution (cible : Docker). De plus, hermes profile create --clone copie le .env de l'instance (clés API, jeton Telegram) dans le profil préparé : la 0.6 préparera les profils avec un .env vide (R02a ; un .env vide ne retire pas la connexion OAuth de l'instance, d'où R02b : un compte modèle par instance attribuée explicitement, contrôlé avant le réveil), posera un verrou contre la double préparation, choisira le profil dans l'entreprise seulement, rendra la vue « instances » sans effets de bord et gardera la passerelle Telegram unique.

Leçons apprises en construisant

  • Le manifeste du serveur exige jobKey (pas key) ; le valider avec le schéma zod de @paperclipai/shared avant d'installer.
  • Le worker doit finir par runWorker(plugin, import.meta.url), sinon le processus sort aussitôt (code 0) et Paperclip marque le plugin en erreur.
  • Une dépendance CommonJS (yaml) dans un bundle ESM a besoin d'un createRequire en bannière esbuild.
  • paperclipai plugin init plante (paquets manquants) : squelette écrit à la main.
  • Les jobs planifiés tournent sans périmètre entreprise : config.get / agents.list y sont refusés → le job relit les instances mémorisées dans l'état du plugin.
  • Paperclip lance le worker sans HOME : utiliser os.homedir().
  • Pas d'emplacement de plugin sur les agents dans cette version ; les menus de l'agent appartiennent à l'adaptateur → d'où l'adaptateur Hermes Control qui remplace l'intégré.
  • Paperclip refuse une mise à jour de plugin qui ajoute une capacité (ui.action.register) : désinstaller puis réinstaller (même identifiant conservé).
  • hermes profile create --clone copie les liens relatifs des skills tels quels : depuis profiles/<agent>/skills ils pointent un cran trop haut (vers les liens de l'instance) — on compare les cibles réelles, pas le texte du lien.
  • Les hooks listSkills / syncSkills ne reçoivent que l'identifiant de l'agent (pas son nom) → carte partagée agents.json. L'adaptateur Hermes officiel ignore HERMES_HOME pour les skills (il lit $HOME/.hermes/skills).
  • Un adaptateur externe s'installe par chemin local (adapter install --payload-json '{"packageName":"…","isLocalPath":true}') et doit exporter createServerAdapter().
